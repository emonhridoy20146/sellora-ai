# 0017 — SMS: gateway adapters, Sellora SMS paid from the wallet, order messages, opt-outs

**Status:** accepted (2026-10-29)

**Context.** Bangladeshi shoppers expect a text after they order ("we got your order", "your
parcel is on the way"), and sellers use SMS to bring back shoppers who left without ordering
and to announce offers. Sellers either already have an account with a Bangladeshi SMS
company (BulkSMSBD, Alpha SMS / sms.net.bd, SSL Wireless and others, which sell prepaid SMS
and register "masking" sender names such as `NAKSHIGHOR` with the mobile operators) or want
to buy SMS from Sellora without dealing with one. The plan (section 6) asks for adapters for
Bangladeshi providers and Twilio, merchants using their own gateway or Sellora's prepaid SMS
managed by the super-admin, and consent for marketing. SMS cost real money per message, an
SMS sent twice is a visible mistake, and Bangla text costs about twice as much as English
because it needs Unicode.

**Decision.**

- **One adapter per provider behind `SmsProvider`** (`src/modules/sms/providers`): BulkSMSBD,
  Alpha SMS (sms.net.bd), SSL Wireless (ISMS v3) and Twilio, written from each provider's
  published API. An adapter knows the provider's credentials, number format, how to send one
  message, how to read its answer and, where the provider has one, a balance call used to
  check credentials. Errors are classified as `rejected` (the number or text was refused;
  nothing was sent), `auth`, `balance` (the provider account is empty), `busy`,
  `unavailable` (safe to try again) and `uncertain` (the request may have reached the
  provider). How HTTP failures sort on a send: a refused connection and HTTP 503 (the
  provider turned the request away before doing anything) are `unavailable`; 429 is `busy`;
  a timeout, a dropped connection or any other 5xx is `uncertain`, because the provider may
  have sent the message before failing to answer. On calls that send nothing (balance
  checks) the same failures are `unavailable`. Addresses are environment settings (`SMS_*_BASE_URL`, `SMS_HTTP_TIMEOUT_MS`)
  defaulting to each provider's published address, so a local stand-in can answer instead.
- **Two routes.** A business sends either through **its own gateway** (credentials checked
  with the provider, stored AES-256-GCM encrypted, never returned; its own sender id; the
  provider bills it directly) or through **Sellora SMS**: the platform's gateway, set up by
  the super-admin in Admin › SMS, paid from the business's wallet. Or SMS is off (the
  default).
- **Sellora SMS is priced per part.** A message is split into parts the way phones and
  operators count them: GSM-7 text is 160 characters (153 per part when longer), anything
  else (Bangla, emoji) is Unicode at 70 (67 per part). The super-admin sets the price per
  part per currency, for the shared sender and for a business's own sender name, and what
  each part really costs Sellora, so Admin › SMS shows SMS revenue, cost and profit like AI
  credits do. Prices live in the database, not in code; the seeded prices are placeholders.
  Before a message is handed to the worker the price is **held** in the wallet; when the
  provider accepts it the hold becomes an `sms_usage` debit; when it fails the hold is
  released. SMS are paid with wallet cash only: the free AI credit stays for AI (ADR 0005).
  An empty wallet fails the message with `insufficient_balance` instead of sending on credit.
- **Sender names need approval.** On Sellora SMS a business sends from the platform's
  shared sender unless it asks for its own name (3–11 letters and digits). The request
  waits in Admin › SMS › Sender names; the super-admin registers it with the provider (an
  operator process that takes days) and then approves it, or refuses it with a reason the
  owner reads. On its own gateway a business types the sender id its provider approved.
- **Every message is written down before it is sent** (`sms_messages`): number, text,
  purpose (`order_placed`, `order_confirmed`, `order_shipped`, `order_delivered`,
  `order_cancelled`, `test`, and later cart recovery and campaigns), route, sender, parts,
  price, status, provider id and error. A unique `(orgId, key)` index makes each message
  exist once (`order:<id>:shipped`), so an event that fires twice, or a retried job, never
  texts the shopper twice. Sending claims the message (`queued` → `sending`) before calling
  the provider. A provider that does not answer leaves the message `unknown` and it is not
  sent again; the business is not charged for it. Messages are kept for a year.
- **Order messages.** In Settings › SMS a business turns on texts for order placed,
  confirmed, shipped (with the courier's tracking link), delivered and cancelled, each with
  an editable template in English or Bangla using `{name}`, `{order}`, `{total}`, `{shop}`,
  `{phone}`, `{courier}` and `{tracking}`. Unknown placeholders are refused when saving, and
  the editor shows how many parts and how much each message costs. Messages go to the
  order's customer phone when it is a mobile number the route can reach (Bangladeshi
  providers: Bangladeshi mobiles only).
- **Opt-outs.** `sms_opt_outs` lists numbers a business must not send marketing messages to
  (cart reminders and campaigns, which come later). Marketing texts carry a short link
  (`<web app>/u/<code>`) to a page that asks before stopping messages, so link scanners and
  previews cannot opt anyone out; staff can also stop or allow a number. Order messages are
  service messages and are still sent.
- **Limits.** Each business can send at most `SMS_DAILY_LIMIT` messages a day by default
  (the super-admin can change it per business), so a mistake or a stolen account cannot
  drain a wallet or the platform's provider balance. Sending a test message is rate limited.
- **Module.** Order messages and the SMS settings belong to the `commerce` module (every
  plan with orders); cart reminders and campaigns will need `marketing`.

**Why.** Adapters keep provider details in one file each, like couriers (ADR 0013). Holding
the price before sending means many messages at once can never overdraw a wallet, and the
`sms_usage` ledger entry gives the merchant and the super-admin the same record. Writing the
message down with a unique key before sending is what makes "never twice" true when events,
jobs or people repeat themselves. Counting parts the operators' way makes the price the
merchant sees match what the provider charges.

**Limits (v1).**

- The adapters were written from the providers' public documentation and tested against
  recorded answers and a local stand-in (`scripts/sms-stand-in.mjs`). **No real SMS has been
  sent** yet: each needs a provider account (and a registered sender) first.
- Delivery reports: only Twilio reports delivery (by a signed callback). The Bangladeshi
  providers' answer means "accepted by the provider"; Sellora shows that as "sent". A
  message charged when the provider accepted it and later reported undelivered is marked
  failed but **not refunded**: the provider charged Sellora for it too. A refund policy for
  those can be added if businesses ask.
- The super-admin's test send from Admin › SMS goes through the platform account directly:
  it is recorded in the audit log, not in any business's message list, and nobody is
  charged.
- No OTP messages yet (OTP checks at checkout come with payments), no replies, no email.
